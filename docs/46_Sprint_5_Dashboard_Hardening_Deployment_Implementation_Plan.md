## 3. Security, database, and deployment rules

### S5-002 implemented metric contract

S5-002 provides aggregate-only, Administrator-scoped metrics: active non-deleted rooms; active rooms with a `checked_in` booking-room association; calculated available active rooms (`active - occupied`); local-day arrivals/departures; non-deleted `pending` and `confirmed` bookings; `submitted` payment attempts awaiting review; `pending` reviews awaiting moderation; and unread notifications for the current Administrator only. No Guest fields or list records are returned. A reporting day is Asia/Kathmandu midnight inclusive through the following local midnight exclusive; the service carries those UTC instants and the repository converts them back to local date parameters for DATE columns. Financial/revenue, tax, refund, collected, invoiced, and verified-amount metrics are intentionally omitted pending owner/architect approval. Existing indexes include booking date/status, payment status, review moderation, and notification user/unread indexes; S5-002 adds no index or migration pending measured EXPLAIN evidence.

S5-002 verification evidence: `bookings.check_in` and `bookings.check_out` are DATE columns, so they represent the Kathmandu reporting date rather than UTC instants; the UTC range `[2026-07-31 18:15:00, 2026-08-01 18:15:00)` maps to local DATE parameters `[2026-08-01, 2026-08-02)`. MariaDB EXPLAIN on the local test database selected the existing notification unread, review public, payment status, booking status, booking-room unique, room primary-key, and booking date-range indexes where applicable. The active-room and departure subqueries reported `ALL` for one-row fixture tables; no temporary table or filesort appeared. This is not representative production-scale evidence and does not justify an index or migration; S5-007 remains the performance-validation gate. Local S5-002 evidence consists of aggregate-only model/service/provider tests, MariaDB repository integration tests, and focused existing domain regressions. No dashboard UI or JSON endpoint is implemented by this ticket.

## S5-005 Prompt A evidence (in progress; not ticket closure)

The executable review confirmed the existing fail-closed authentication, session, CSRF, upload, private-file, token, and no-store controls. Authentication verifies with `password_verify()`, identifies replacement hashes with `password_needs_rehash()`, and creates replacements with `password_hash(PASSWORD_DEFAULT)` only after a successful eligible login. Missing accounts use a runtime dummy hash. Two direct unit regressions now explicitly cover malformed stored password hashes and deleted/non-Administrator accounts; every case returns the same generic credential rejection, establishes no identity, records no successful login or rehash, and excludes plaintext passwords and stored hashes from the security-log context. The private, locked, expiring rate limiter derives a SHA-256 filename from packed direct `REMOTE_ADDR`; it supports IPv4/IPv6, validates state strictly, resets on success, and stores neither username/password nor raw IP.

Application session timeouts are enforced (default local values: 1,800 seconds inactivity and 43,200 seconds absolute lifetime); protected environments require explicit positive values and secure cookies. Sessions are strict, cookie-only, trans-SID-disabled, HttpOnly, private-storage backed, and rotate the session ID and CSRF token on successful login; logout destroys server state and expires the cookie. Registered state-changing public and Administrator routes are CSRF-protected, with generic no-store failures. Ownership uses the authenticated Administrator session; payment proofs derive their private path from persisted data, notification operations are owner-scoped, booking/review tokens are record-scoped, and raw review tokens are SHA-256-hashed before persistence. Upload validation retains MIME/content/image decoding, approved limits, randomized destinations, containment, cleanup, and safe private-file headers. Focused local evidence retains three Windows-only symlink skips (payment-proof reader, gallery storage root, and gallery upload temporary-file defenses); those cases were not executed on this host.

Protected and sensitive responses retain route-specific `Cache-Control: no-store`; private proof/image responses use safe content type/disposition and `X-Content-Type-Options: nosniff`, while invoice responses additionally use their existing `X-Frame-Options: SAMEORIGIN` and `Referrer-Policy: no-referrer`. No global header policy, CSP, HSTS, Permissions-Policy, or global Referrer-/Frame-Policy was added. Direct `REMOTE_ADDR` is deliberately used and forwarded headers are not trusted; cPanel/reverse-proxy topology, peer-IP visibility, private writable directory checks, HTTPS, and actual protected timeout values remain S5-010 deployment checks. ## S5-006 backup and restore implementation evidence

The backup-facing command is `php bin/backup-database.php`; `--help` is the only supported option. It creates one logical SQL backup beneath the private `storage/backups` directory and returns only the generated SQL basename, matching manifest basename, byte count, lowercase SHA-256, UTC creation timestamp, and bounded native tool family/version. Generated SQL names use `tara-guest-house-YYYYMMDDTHHMMSSZ-<12 lowercase hex>.sql`; callers cannot select a directory, filename, database, connection value, executable, or native flag. Exit code `0` means help or successful backup, `1` is a sanitized operational failure, and `2` is invalid usage.

Credentials are written temporarily to a randomized, private `.db-client-<24 lowercase hex>.cnf` file with restrictive permissions where supported. `--defaults-extra-file=<temporary path>` is always the first native argument; host, port, username, and password are absent from the argument list and command output. Native execution uses `proc_open()` with an executable/argument array and `bypass_shell`; no joined shell command or shell wrapper is used. Resolution order is `mariadb-dump`, `mariadb-dump.exe`, `mysqldump`, then `mysqldump.exe`, each probed only with `--version`. MariaDB backup arguments are `--single-transaction`, `--quick`, `--skip-lock-tables`, `--hex-blob`, and `--default-character-set=utf8mb4`; the MySQL profile additionally uses `--column-statistics=0` and `--no-tablespaces`. The validated configured database name is the final argument.

Native stdout is directed to a same-directory `.sql.part` file. An exit code of zero is insufficient: the output must be a non-empty regular file, must not be whitespace-only, and must contain a practical MySQL/MariaDB logical-SQL indicator within a bounded 65,536-byte prefix. The service calculates exact bytes and lowercase SHA-256, writes deterministic manifest version 1 JSON to `.manifest.json.part`, flushes and closes it, and uses same-directory finalization. It refuses existing final or temporary paths, always removes the temporary client option file, cleans partial output after failure, and removes a finalized SQL file if manifest finalization fails, preventing a newly created orphaned pair.

Focused local automated evidence uses only fake native execution and covers successful metadata/integrity output, strict CLI usage, help without credential loading, SQL-output rejection, process failures, overwrite refusal, finalization cleanup, and bounded exception/output behavior. The combined backup-focused result is 38 tests and 217 assertions with one skip: current Windows/filesystem permissions do not permit the directory-symlink escape test. This is local automated evidence only, not GitHub CI, restore, staging, cPanel, or production evidence.

The authorized real local read-only smoke test was not executed. Validated configuration was local/testing, the configured database name matched the local/test safety policy, and the resolved backup root was private; however, PHP reported `storage/backups` as not writable and the directory had the Windows read-only attribute. The safety precondition therefore failed before executable resolution or native invocation. No smoke SQL, manifest, client-option, or `.part` file was generated, so no runtime cleanup was required and no pre-existing backup was removed. Directory permissions were not changed as part of this ticket.

Restore tooling is available through `php bin/restore-database.php <generated-backup-basename.sql>`. Basename-only invocation is preflight and does not import SQL: it reuses the private backup root and strict manifest parser, verifies the logical-SQL prefix, exact bytes and SHA-256, checks that the configured application database already exists, requires zero base tables and zero views through parameterized `information_schema` queries, and probes the restore client only with `--version`. The configured database is the only target; callers cannot supply paths, manifests, targets, connection values, native flags, force mode, or empty-target overrides. Preflight output contains bounded metadata and states `Restore not executed.`

Execution requires the deterministic arguments `--execute --confirm-database=<exact configured name>`. Staging and production additionally require `--confirm-environment=<exact environment>`; confirmation errors occur before restore-service construction and native execution. `DatabaseRestoreService::execute()` never trusts an earlier result: it reruns the complete file, manifest, checksum, target-existence, zero-table/zero-view, and client-availability preflight immediately before import. Only after that succeeds does it create the temporary private option file. Restore arguments are exactly `--defaults-extra-file=<private option path>`, `--default-character-set=utf8mb4`, and the configured database; the verified SQL file is opened directly as `NativeProcessRequest` stdin, with no shell redirection or joined command. The option file is always removed, and the SQL backup and manifest are retained after success or failure. The service and command expose only bounded basename/integrity/tool/timestamp metadata and sanitized failures.

No real restore was executed for this implementation evidence. Automated execution coverage uses fake native processes and mocked database metadata only; no development database connection, data change, schema change, migration, or native import occurred. No restore web/API trigger, automatic database replacement, `DROP DATABASE`, `CREATE DATABASE`, `TRUNCATE`, scheduling, retention automation, encryption, or offsite/cloud upload was added. Safe real restoration remains an operations exercise against a disposable empty test database. Production/cPanel backup and restore validation, writable-path policy, disaster-recovery evidence, and approval remain deferred to S5-010 and later external gates.

The complete local S5-006 focused result is 108 tests and 945 assertions with one skipped Windows directory-symlink capability test, zero failures/errors/warnings/notices/deprecations, and no PHPUnit stderr. This completes the scoped backup/restore tooling implementation and its local focused gates; ticket closure still requires review and the separately identified CI, disposable-database restore rehearsal, staging/cPanel, and operations evidence.
